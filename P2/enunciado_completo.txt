Práctica 2. Conceptos Avanzados sobre Bases de Datos
Relacionales
Versión 2.1 - 02/10/2026

Introducción
En esta práctica se profundiza en el uso de bases de datos (BBDD) relacionales usando
PostgreSQL. Mediante procedimientos almacenados y triggers, el estudiante aprenderá a
gestionar la persistencia y a trasladar parte de la lógica de negocio hacia la propia base de datos,
reduciendo así la dependencia del código externo y mejorando la consistencia de las operaciones.
Además, se llevará a cabo la optimización de queries.

Objetivos docentes
Tras la realización de esta práctica, el estudiante debe ser capaz de:
●

Desplegar un contenedor Docker con la base de datos en PostgreSQL para su uso.

●

Entender e implementar procedimientos almacenados.

●

Entender y manejar los triggers en una base de datos.

●

Identificar posibles acciones que pueden mejorar el rendimiento de una consulta.

●

Acceder a una base de datos desde Python usando SQLAlchemy.

Tecnologías a utilizar
En esta práctica, se utilizará:
●

Quart como framework ASGI (Asynchronous Server Gateway Interface).

●

Docker como sistema de contenedores para distribuir los servicios.

●

PostgreSQL como sistema gestor de bases de datos (SGBD). Se desplegará en un
contenedor Docker y se arrancará mediante el fichero docker-compose.yml
correspondiente. Se debe usar una imagen oficial de PostgreSQL, que cree el usuario
alumnodb con contraseña 1234 y la base de datos si1.

●

SQLAlchemy (librería Python). Se utilizará como interfaz de acceso a la base de datos en
PostgreSQL desde la API REST.

Tareas a realizar
Se trata de implementar una pequeña plataforma de distribución de contenidos audiovisuales (un
videoclub de películas), donde los usuarios se registrarán y podrán consultar el catálogo de
películas, recargar el saldo de su cuenta, comprar contenidos y realizar valoraciones. Los datos
persistirán en una base de datos.

1. Diseño y carga de la base de datos
El diseño de la base de datos es libre, y cada equipo de estudiantes deberá implementarla según
su criterio. No obstante, el diseño debe cumplir con los requisitos que se enumeran a continuación.

1.1. Requisitos
El sistema deberá cumplir con los siguientes requisitos mínimos:
●

Gestión de usuarios. El sistema deberá permitir gestionar diferentes usuarios que
interactúen con la aplicación. Los usuarios deberán poder consultar información y realizar
determinadas operaciones sobre las películas del videoclub.

●

Catálogo de películas. El sistema deberá gestionar todo lo relacionado con las películas,
actores y directores. También permitirá realizar diferentes consultas sobre estos
elementos.

●

Recursos y disponibilidad. El sistema deberá gestionar la compra de películas por parte
de usuarios. Por tanto, deberá determinar si una película está disponible, cuántas unidades
existen, etc., es decir, llevar un stock. Las compras de películas se realizarán mediante la
metáfora del carrito de la compra. A la hora de pagar, hay que tener en cuenta aspectos
como el saldo disponible del usuario, la reducción del stock, etc.

Se debe realizar un diseño formal de la base de datos mediante un diagrama E-R (Entidad
Relación). A partir de esta base de datos, se debe construir la siguiente funcionalidad:
●

Gestión de los recursos y disponibilidad mediante triggers. Por ejemplo, cada vez que se
añada o elimine un producto del carrito, deberá actualizarse el stock, el precio final del
carrito y/o cualquier otra acción necesaria.

●

Queremos evitar problemas de sincronización con el usuario. Por ejemplo, cada vez que
se pague un carrito, queremos que su coste se descuente automáticamente del saldo del
cliente mediante triggers.

2. Construcción de la API
En esta práctica se utilizará la librería SQLAlchemy para realizar queries contra el SGBD desde la
API REST desarrollada en Python. Por tanto, se deberá implementar la funcionalidad necesaria
para que los usuarios se autentifiquen y puedan consultar el catálogo de películas, recargar el
saldo de su cuenta, comprar contenidos y realizar valoraciones. Para ello, igual que en la práctica
anterior, usaremos un enfoque basado en microservicios.

2.1. Requisitos de implementación
El acceso a la base de datos debe realizarse exclusivamente mediante la librería SQLAlchemy,
usando la interfaz Core (https://docs.sqlalchemy.org/core), que ofrece una capa de abstracción
más cercana al lenguaje SQL, permitiendo construir y ejecutar sentencias SQL de forma explícita.
Dado que la API se publicará y ejecutará con Quart, que utiliza un modelo asíncrono de
procesamiento, se debe usar la extensión para asincronismo de SQLAlchemy
(https://docs.sqlalchemy.org/orm/extensions/asyncio.html). Esto implica:
●

Usar async/await. En particular, todas las operaciones que accedan a la base de datos
deben realizarse dentro de funciones declaradas como async, utilizando await cuando
corresponda. Se debe mantener la coherencia del flujo asíncrono a lo largo del código.

●

Utilizar las extensiones asyncio en la configuración del acceso a base de datos. El
siguiente fragmento de código muestra una posible configuración para acceso asíncrono
que puede servir de inspiración.

2.2. Funcionalidades mínimas de la API
Se crearán dos microservicios que se ejecutarán en dos contendedores independientes,
programando los endpoints necesarios y separando las definiciones de la API según se indica a
continuación. Los dos microservicios accederán a la misma base de datos.

2.2.1. API de usuarios
El servicio de gestión de usuarios almacenará el nombre de usuario y la contraseña cifrada. Tendrá
además otros campos adicionales, como la nacionalidad (país) del usuario o el saldo de su cuenta,
etc. La API de usuarios debe implementar las operaciones de crear y borrar un usuario, además
de actualizar su saldo. También debe permitir hacer login y logout para actualizar el token de
sesión. La API de usuarios se implementará en un fichero user.py.

2.2.2. API principal
La gestión y el acceso al videoclub se realizará usando también SQLAlchemy Core. Todas las
sentencias SQL se escribirán manualmente y se ejecutarán usando el concepto de prepared
statements (consultas parametrizadas con un diccionario de valores), utilizando el motor
asíncrono configurado con text(), execute() y await. Esto aporta mayor seguridad, evitando
ataques de inyección SQL al separar los datos de la lógica de la consulta, además aporta mayor
eficiencia, ya que las consultas pueden ser “precompiladas”, reduciendo el tiempo de análisis y
planificación por parte del motor de la base de datos. De esta forma, el código es también más
mantenible.

Gestión de recursos principales, soportando la creación y borrado de películas.

2.

Obtener un listado de películas por algún criterio específico.

2.3. Cliente de prueba
Para evaluar estos dos microservicios, se debe crear un client.py que compruebe que se cumple
con toda la funcionalidad implementada. El cliente deberá ser lo suficientemente completo como
para probar todos los casos y los errores (tolerancia a fallos) correspondientes.

3. Optimización
En este último apartado vamos a estudiar aspectos de optimización. Para ello, vamos a utilizar la
sentencia EXPLAIN sobre la consulta …/ventas/<año>/<país> para estudiar el plan de ejecución
de la consulta. Con la sentencia EXPLAIN se puede identificar cómo mejorar el rendimiento de una
consulta (por ejemplo, mediante la creación de un índice). Compara el resultado de EXPLAIN antes
y después de hacer los cambios necesarios. Prueba distintas estrategias y discute los resultados.
Para ello, se debe entregar un script SQL llamado optimizacion.sql con todas las sentencias
necesarias para optimizar la consulta comentada.
